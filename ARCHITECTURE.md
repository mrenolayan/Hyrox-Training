## The one rule that matters most: three layers, strictly separated

```
┌─────────────────────────────────────────────────────────────┐
│  UI components (React)                                        │
│  - render the screens the coach likes (tabs, theme, etc.)    │
│  - read data through hooks; never import the Supabase client  │
└───────────────▲─────────────────────────────────────────────┘
                │ calls plain functions / hooks
┌───────────────┴─────────────────────────────────────────────┐
│  lib/*.js  — business logic (NO React, NO Supabase)          │
│  - plan generation, pace math, unit conversion,              │
│    HRV deload trigger, wall-ball ladder, phase structure     │
│  - plain functions → easy to unit-test in isolation          │
└───────────────▲─────────────────────────────────────────────┘
                │ called by db layer / hooks to shape data
┌───────────────┴─────────────────────────────────────────────┐
│  lib/db.js  — the ONLY module that talks to Supabase         │
│  - every read/write goes through here                        │
│  - if you grep for "supabase" outside this file, that's a bug │
└─────────────────────────────────────────────────────────────┘
```

**Why this matters for you (a beginner):** when something breaks, the layer tells
you where to look. Wrong number on screen → `lib/` math. Data won't save →
`lib/db.js`. Button in wrong place → UI. You never have to read all three at once.

### Layer responsibilities

**`lib/db.js` — data access (sole Supabase boundary)**
- Creates the one Supabase client.
- Exposes named functions: `getAthletes()`, `getAthlete(id)`, `getPlan(athleteId)`,
  `saveLog(...)`, `upsertPlanEntries(...)`, `getTeamLogs(...)`, etc.
- Returns plain JS objects/arrays. Never returns raw Supabase responses or query
  builders. The rest of the app does not know Supabase exists.
- Reason: if we ever change databases, only this file changes.

**`lib/*.js` — business logic (pure functions, no I/O)**
- `lib/plan.js` — the *training rules as data*: session templates (extracted
  from the existing 12-week Walker/Hung plans), the phase rhythm, wall-ball
  ladder, and HRV deload trigger. `generatePlan(team, plan, athletes)` builds a
  plan of **any length procedurally** — there is no hand-authored content past 12
  weeks, so 8/16/20 are generated by scaling base/build blocks (deload ~every
  4th week) + a 3-week peak+taper. It returns a draft normalized plan **object**
  (does NOT write to the DB — the caller persists via `db.js`). Separating "the
  rules" from "this team's instance" is explicit in the spec.
- `lib/pace.js` — pace parsing (`parsePace`, `paceLabel`) and unit conversion
  (km↔mi, kg↔lb). Today these live inline in the components; we lift them out so
  they're testable.
- `lib/phases.js` (or part of plan.js) — given a plan length, return the phase
  breakdown (Base / Build / Peak+Taper week ranges). Must handle 20 weeks.
- These are plain functions: input → output, no React, no fetch. You can test
  them in a script with no browser.

**UI components**
- Read via React hooks (e.g. `useAthlete(id)`, `usePlan(athleteId)`) that wrap
  `db.js` calls. Components render; they don't fetch directly.
- Keep the existing visual design and the features listed in PRODUCT.md.

## Tech stack changes

- **Add `@supabase/supabase-js`** as a dependency (today the app talks to Supabase
  via raw `fetch` — we replace that with the official client so we get auth, RLS
  headers, and typed-ish queries).
- Keep Vite + React 18.
- **Env vars** via Vite: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` in a
  `.env.local` (gitignored). Today the URL + anon key are **hardcoded in the
  source** (`HyroxTrainer.jsx:276-277`) — we move them to env. The anon key is
  safe to ship to the browser *only because* RLS restricts what it can do, which
  is why Phase 4 (auth + RLS) matters before we rely on it.

## Auth model (Phase 4)

- Supabase Auth, **magic link** (email, no passwords).
- On login we look up whether the user is a coach or an athlete (see
  `coaches.user_id` / `athletes.user_id` in DATA_MODEL.md) and route accordingly.
- RLS policies (DATA_MODEL.md) become the real security boundary. Until Phase 4,
  development uses permissive policies / the anon key as today — **we do not
  expose real athlete data publicly once auth is wired.**

> ⚠️ **Security window (Phase 1 → Phase 4):** between seeding real data into the
> new tables and turning RLS on, the anon key + permissive policies mean those
> tables are **publicly readable**, same as today's `kv_store`. Mitigation: seed
> with the already-public Walker/Hung data only (no new sensitive PII), and/or
> enable RLS early on any table holding real athlete contact info. Don't put
> emails/phone numbers into seeded rows before Phase 4.

## Data loading / performance

- Coach dashboard loads **athlete summaries** (name, race, next session, %
  complete) — not full plans. Paginate if the list grows.
- Full plan + logs load **lazily** when the coach opens one athlete.
- All foreign keys used for filtering are indexed (see DATA_MODEL.md).

## Migration of existing data (Phase 5)

Today logs/notes/overrides live as JSON strings in a single `kv_store` table,
keyed like `hyrox-team-walker-dc-logs-a0`. Phase 5 reads those blobs, parses
them, and writes normalized rows (`logs`, `coach_notes`, plan edits). We keep
`kv_store` read-only until the migration is verified, then retire it.
